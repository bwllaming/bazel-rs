# Build configuration and configured attributes (Bazel 9.3)

Increment N16a: a native build configuration with the modelled Bazel options,
`config_setting` analysis for `values`/`define_values`, and `select()`
resolution during analysis. Increment N16b: Starlark build settings on the
command line, `config_setting(flag_values = ...)`, and analysis of `alias`,
`label_flag` and `label_setting`. Increment N16c: platforms — the target
platform, `constraint_setting`/`constraint_value`/`platform` analysis,
`config_setting(constraint_values = ...)` and `constraint_value` select()
keys (docs/PLATFORMS.md). Everything else that a configuration would
influence keeps failing explicitly; nothing is ignored.

Pinned source: `/tmp/opencode/bazel-9.3-reference` (e89755b, Release 9.3.0).
Paths are relative to `src/main/java/com/google/devtools/build/lib/`. Code:
`src/configuration.rs`, `src/configured_attributes.rs`, `src/config_setting.rs`,
`src/engine.rs` (analysis order, aliases), `src/starlark_options.rs` (build
settings), `src/bazel_options.rs` (generated by
`scripts/extract_bazel_options.py`).

## Configuration

One top-level configuration per `build` invocation, plus the exec
configurations its exec-transition edges create (below; no other
transitions). Modelled options, with Bazel's defaults and converters:

| Option | Default | Converter / normalization | Source |
| --- | --- | --- | --- |
| `-c`/`--compilation_mode` | `fastbuild` | `fastbuild`, `dbg`, `opt` (case-insensitive EnumConverter) | `analysis/config/CoreOptions.java:396-404`, `CompilationMode.java:24-51` |
| `--host_compilation_mode` | `opt` | like `--compilation_mode`; the exec configuration's compilation mode (below); selectable in `config_setting(values)`; a `query` option (CoreOptions) | `CoreOptions.java:406-417` |
| `--[no]stamp` | `false` | BooleanConverter (`true/1/yes/t/y`, `false/0/no/f/n`, any case) | `CoreOptions.java:349-355`, `common/options/Converters.java:46-60` |
| `--define NAME=VALUE` | `[]` | AssignmentConverter, repeatable; last value per key, sorted by key | `CoreOptions.java:255-267, 1245-1248`, `FragmentOptions.java:100-113` |
| `--strip` | `sometimes` | `always`, `sometimes`, `never` | `rules/cpp/CppOptions.java:337-347`, `CppConfiguration.java:119-134` |
| `--[no]force_pic` | `false` | BooleanConverter | `CppOptions.java:218-227` |
| `--platforms` (`--experimental_platforms`) | `--host_platform` | comma list, empty entries dropped, `//` prefixed unless `/`/`@`; only the first entry is kept (the target platform); empty becomes `--host_platform` | `analysis/PlatformOptions.java:82-96, 189-212`, `skyframe/config/PlatformMappingValue.java:154-158`, `CoreOptionConverters.java:143-158, 331-361` |
| `--host_platform` (`--experimental_host_platform`) | `@bazel_tools//tools:host_platform` | label; empty means the default | `PlatformOptions.java:46-64, 218-227` |
| `--extra_toolchains` | `[]` | repeatable comma list of target patterns (empty values kept, an empty value adds nothing); duplicates keep the last copy; part of the identity only when non-empty; not a `query` option (docs/TOOLCHAINS.md) | `PlatformOptions.java:98-116, 164-201`, `common/options/Converters.java:253-287` |

Values that resolve to `@@bazel_tools//tools:host_platform` (or are empty)
give the default configuration, exactly like the unset options (both become
`platforms = [host]` after platform mapping). Other values are configurations
of their own whose platforms are resolved and validated as platform targets
(PlatformFunction semantics, docs/PLATFORMS.md): an explicit non-default
target or host platform before analysis, the default host platform only where
a constraint needs it. `@bazel_tools` is always visible from the main
repository (an implicit dependency of every module) for option conversion,
also when the native module graph does not materialize it; resolving the
default host platform then fails explicitly (docs/PLATFORMS.md).

Command-line forms follow `OptionsParserImpl.identifyOptionAndPossibleArgument`
(`common/options/OptionsParserImpl.java:756-850`): `--name=value`,
`--name value`, `-c value`, `--name`/`--noname` for booleans (`--stamp true`
makes `true` a target pattern). Errors are Bazel's: exceptions that carry the
invalid argument are printed `ARG :: MESSAGE` (`runtime/BlazeOptionHandler.java:104,
628-637`) — `--nostamp=0 :: Unexpected value after boolean option: --nostamp=0`,
`--nocompilation_mode :: Illegal use of 'no' prefix on non-boolean option: ...`,
`-c=opt :: Invalid options syntax: -c=opt` (any `-x...` other than `-x`/`-x-`,
and `--=v`) — while `Expected value after ARG` and converter failures
(`While parsing option FORM: MESSAGE`) have no prefix. Label options are
converted with the main repository mapping. Every other option keeps the
existing `unsupported option ...; options are never silently ignored` error.
`query` accepts and validates the modelled CoreOptions (`-c`, `--[no]stamp`,
`--define`; `runtime/commands/QueryCommand.java:59-67`, which does not add the
configuration fragments' options, `runtime/BlazeCommandUtils.java:74-98`) and
ignores them (query is configuration-independent); `--strip` and
`--force_pic` stay unsupported for `query`, and `--platforms`/`--host_platform`
are Bazel's `ARG :: Unrecognized option: ARG` (query registers no
PlatformOptions; docs/PLATFORMS.md). A
workspace-root `platform_mappings` file (read by Bazel by default) fails the
build explicitly: platform mappings are not modelled.

**Identity.** `ConfigId` is SHA-256 over a versioned canonical JSON
serialization of the modelled values plus the Starlark build settings that
differ from their defaults. Equal values give equal identities regardless of
spelling (`-c OPT` = `--compilation_mode=opt`, `--//:s=red` with default `red`
= unset). Analysis is keyed by `ConfiguredTargetKey { label, config }`
(below). The options of the exec configuration — `host_compilation_mode`
(default `opt`), `is exec configuration` (false) and `platform_suffix`
(null) — are omitted from the serialization at their defaults, so every
existing identity is byte-identical (pinned in `src/configuration.rs` for the
default, `-c dbg` and `-c opt`).

## Starlark build settings (`src/starlark_options.rs`)

Arguments starting with `--//`, `--no//`, `--@` or `--no@` are skipped by the
native options parser and kept in order (`OptionsParser.STARLARK_SKIPPED_PREFIXES`,
`common/options/OptionsParser.java:111-112`, `OptionsParserImpl.java:535-550`);
`-//...` and `-@...` fail with Bazel's `Invalid options syntax: ARG` plus the
negative-target-pattern note (`:515-525`). `--` ends the options
(`:528-531`): later arguments are target patterns, and a `-` prefix makes a
negative pattern whose syntax is checked with Bazel's label parser
(`invalid package name '-//': ...`) — subtracting patterns is not implemented
natively. A `--NAME[=V]` that is not a native option of this profile is
`ARG :: Unrecognized option: ARG` (`OptionsParserImpl.java:776-824`) when NAME
(also without a `no` prefix) is neither the name nor the old name of any
`@Option` of the Bazel 9.3 source tree and SpellChecker would suggest nothing
even among all of them (`src/bazel_options.rs` `ALL_OPTION_NAMES`, a superset
of the command's options); otherwise it keeps the explicit "unsupported
option" error. For `build` they are parsed after
the native options and before target patterns
(`runtime/BlazeCommandDispatcher.java:765-776`) by
`StarlarkOptionsParser.parseGivenArgs` (`runtime/StarlarkOptionsParser.java:159-342`):

* Forms: `--NAME=VALUE`; `--NAME` / `--noNAME` for boolean settings only
  (`true`/`false`); `--noNAME` of another type is `NAME :: Illegal use of 'no'
  prefix on non-boolean option: NAME`, `--NAME` alone is `--NAME :: Expected
  value after --NAME`, with BlazeOptionHandler's `. Did you mean --NAME=NEXT?`
  when the next command argument is not an option
  (`runtime/BlazeOptionHandler.java:428-440`; NEXT is then a target pattern).
* Loading: NAME is loaded as a target pattern from the working directory
  (`SkyframeExecutorTargetLoader`, `BlazeOptionHandler.java:371-410`), which
  loads its package; a loading error is `NAME :: Error loading option NAME:
  MESSAGE`, with the label parser's syntax errors (`--no//:b=true` loads
  `no//:b`: `invalid package name 'no//': package names may not end with '/'`)
  and `No repository visible as '@R' from main repository` for an unknown
  apparent repository. Like any target pattern, a loaded rule with an explicit
  `deprecation` warns `LOC: target 'L' is deprecated: MSG`
  (`TargetPatternPhaseFunction.java:255-275`), only when the option is given. Unconfigured `alias` chains are followed (`loadBuildSetting`,
  `:350-417`): an alias whose `actual` is a `select()` fails (`Failed to load
  build setting 'NAME' as it resolves to an alias with an actual value that
  uses select(): CHAIN. ...`), as do alias cycles (`... due to a cycle in alias
  chain: A -> B -> A`) and non-settings (`NAME :: Unrecognized option: A -> B`,
  for files and other rules).
* Every argument is loaded before any value is converted. Settings declared
  with `flag = False` (`bool_setting`, ..., `label_setting`) are `Unrecognized
  option: LABEL=VALUE` (`:185-189`). Values convert with
  `BUILD_SETTING_CONVERTERS` (`analysis/config/CoreOptionConverters.java:76-127`):
  BooleanConverter, `StarlarkInt.parse(s, 0)` (`0x`/`0o`/`0b`, no leading `0`),
  strings, comma-separated lists (`""` is `[]`, empty elements kept), labels
  `//`-prefixed unless starting with `/` or `@` and resolved with the main
  repository mapping. A failure is `While parsing option LABEL=VALUE: 'VALUE'
  is not a TYPE` (`boolean`, `int`, `string`, `list(string)`, `label`).
  Repeated non-repeatable settings keep the last value; `repeatable` string
  lists accumulate. LABEL is the setting's canonical form, also through
  aliases.
* Only values different from the default are stored
  (`StarlarkOptionsParser.java:232-254`), so a value equal to the default gives
  the default configuration identity. Ints outside the signed 64-bit range
  (Bazel accepts any `StarlarkInt`) fail explicitly; `allow_multiple` settings
  are not modelled (rejected when declared, docs/BUILD_SETTINGS.md).

`query` does not analyze, so Bazel never parses its Starlark options
(`BlazeOptionHandler.java:417-423`): the native `query` accepts and ignores
them, even for settings that do not exist.

**BuildSettingProvider.** Every build-setting target carries the native
provider `{label, type, default, is_flag, repeatable}`
(`analysis/BuildSettingProvider.java:27-58`): Starlark rules with
`build_setting` (`analysis/RuleConfiguredTargetBuilder.java:250-259`) and
`label_flag`/`label_setting` (`rules/LateBoundAlias.java:66-79`). It is not
visible to Starlark; skylib's `BuildSettingInfo` remains its own Starlark
provider. `ctx.build_setting_value` is the configured value: the command-line
value, else `build_setting_default` (`analysis/starlark/StarlarkRuleContext.java:738-757`).

**Output paths.** Generated files live under `bazel-out/rust-<compilation_mode>/bin`
(Bazel's `<cpu>-<mode>` mnemonic, e.g. `k8-fastbuild`, with the native
profile's fixed `rust` part — a documented divergence). The default
configuration keeps `bazel-out/rust-fastbuild/bin`, so existing artifact paths,
action keys and caches are unchanged; options without an output-path effect
(`--stamp`, `--define`, Starlark settings, ...) reuse the same action keys
unless a resolved attribute changes an action. Bazel adds no `-ST-` suffix
for them either: the default `diff_against_dynamic_baseline` naming
(`analysis/config/CoreOptions.java:759`) hashes only options that differ from
the baseline (`analysis/config/OutputPathMnemonicComputer.java:160-178`), and
the baseline is the top-level target configuration itself
(`analysis/BuildView.java:280`). The root is a property of each configured
target's configuration (below).

## Configured-target keys and output roots (N18a)

Increment N18a makes the configuration of every analyzed target explicit,
without any visible behavior change; exec transitions (N18b), Starlark 1:1
transitions (N18c) and split transitions/exec groups (N18d) build on it.
Code: `src/config_registry.rs`, `src/engine.rs`, `src/analysis.rs`,
`src/analysis_runtime.rs`, `src/label.rs`.

* **Registry.** `Configurations` interns the build's configurations by
  `ConfigId` (`Arc<Configuration>`): the top-level configuration (requested
  targets are analyzed in it), the exec mnemonic baseline (N18b) and
  the output path mnemonic of each configuration.
* **Mnemonics** (`OutputPathMnemonicComputer.computeMnemonic`,
  `analysis/config/OutputPathMnemonicComputer.java:174-245`):
  `{cpu}-{compilation_mode}[-{platform_suffix}][-ST-{12 hex}]`. The CPU
  descriptor of target configurations is `rust`, standing for Bazel's
  `--cpu` (`k8`; divergence D1, which keeps `rust-fastbuild`); exec
  configurations use their platform (below). `compilation_mode` and
  `platform_suffix` are explicit in the path, every other option (native or
  Starlark) that differs from the baseline — the top-level configuration — enters the
  `ST-` hash (`computeNameFragmentWithDiff`, `:286-318`: sorted
  `//command_line_option:NAME=VALUE` / `LABEL=VALUE` / `LABEL@null`
  strings, each framed like `Fingerprint.addString`, SHA-256, 12 hex digits).
  The top-level configuration is its own baseline, so its root stays
  `bazel-out/rust-fastbuild/bin` (default), `bazel-out/rust-dbg/bin` or
  `bazel-out/rust-opt/bin`. Exec configurations use the exec baseline (the
  exec transition section below). **Divergence:** the native `ST-` hash
  follows Bazel's algorithm over the native option set, names and value
  strings only; Bazel's hashes every differing Bazel option (and Java
  `toString` values the native profile does not model), so the two can never
  be equal, even where both have a hash.
* **Output roots** come from the configured target's configuration: the
  analysis context of a Starlark rule (`ctx.actions.declare_file`), genrule
  outputs, `$(RULEDIR)`/`$(@D)`, the package check of declared outputs and
  `Label::generated_exec_path(root)`. A generated `File`'s root and
  root-relative path are read from its own path, any
  `bazel-out/<mnemonic>/bin` (`short_path`, `declare_file(sibling = ...)`,
  `json.encode(File)`'s `root`). There is no ambient (thread-local) root.
* **Keys.** Every analysis and planning map is keyed by
  `ConfiguredTargetKey { label, config }`: configured nodes, the analysis
  plan, the per-target artifacts, providers and provider files, declared
  artifacts (`(config, exec path)`), output producers (paths stay global, so
  overlapping outputs of different configurations still conflict),
  requested artifacts, the platform memo and the empty-configuration rules,
  the registered toolchains (per configuration), the toolchain contexts and
  the toolchain-implementation memo, cycle detection and the depth limit.
  Cycle reports print each element's own key (`LABEL (CONFIG)`). The
  re-analysis for `ctx.target_platform_has_constraint` resolves the target
  platform of the target's own configuration. Package loading stays
  unconfigured (`Engine::generated`, the output label → generating rule map,
  is a loading fact like Bazel's package targets; the configuration enters
  where the output is resolved to an artifact).
* **Edges.** Requested targets are analyzed in the top-level configuration
  and every dependency edge (attributes, select() keys, toolchain types and
  implementations, platforms, registered toolchains) keeps its parent's
  configuration, except exec-transition edges (N18b, below). Rule
  transitions and Starlark/`config.none()` attribute transitions keep failing
  explicitly.
* **Action identities.** Action ids feed the action cache key
  (`src/action.rs`). They stay `LABEL#N` (`LABEL` for genrules) in the
  top-level configuration and become `LABEL[CONFIG8]#N` (the first eight hex
  digits of the ConfigId) in any other configuration, so the keys and warm
  caches of every existing build are unchanged.
  `tests/configured_target_keys.rs` asserts golden action keys and output
  paths recorded with the pre-N18a binary (default and `-c dbg` builds of a
  genrule/Starlark/toolchain fixture, and `tests/fixtures/basic`); the
  recorded check of the change also ran the new binary on caches populated by
  the old one (all cache hits).

## Exec transition (N18b)

Code: `src/config_registry.rs` (`exec_transition`, exec baseline),
`src/engine.rs` (edges, execution platform, genrule `tools`),
`src/analysis.rs` (`ctx.attr`/`ctx.file(s)` of exec edges),
`src/starlark_options.rs` (`scope`).

**Edges.** The exec transition (ExecutionTransitionFactory) applies to
Starlark `attr.label`/`attr.label_list` with `cfg = "exec"`, `cfg = "host"`
(converted to exec while `--incompatible_disable_starlark_host_transitions`
is false, `analysis/starlark/StarlarkAttrModule.java:521-531`;
`BuildLanguageOptions.java:590-598`; with the option, a Starlark semantics
option of `build` and `query` in BooleanConverter forms, `cfg = "host"` is
the .bzl evaluation error `'cfg = "host"' is deprecated and should no longer
be used. Please use 'cfg = "exec"' instead.`, in the native interpreter's
traceback format),
`cfg = config.exec()` (the default exec group), and genrule `tools`
(`rules/genrule/GenRuleBaseRule.java:89-92`). Only resolved values form
edges: an unselected or empty exec attribute needs nothing.
`config.exec("G")` names an exec group that cannot exist natively (rule
`exec_groups` fail explicitly first, N18d): a rule that uses toolchain
resolution reports Bazel's dependency error `LOC: Attr 'A' declares a
transition for non-existent exec group 'G'`
(`analysis/DependencyResolutionHelpers.java:243-253`,
`analysis/producers/DependencyProducer.java:196-203, 606-655`); otherwise
the transition is a no-op like below. `config.exec("default-exec-group")` is
the default group.

**Execution platform.** The exec transition reads the parent's execution
platform from its default toolchain context
(`DependencyResolutionHelpers.getExecutionPlatformLabel`, `:223-241`). A
parent without toolchain contexts — a rule that does not use toolchain
resolution (build-setting rules, `alias`, `label_flag`/`label_setting`,
platform/constraint/toolchain rules, rules inside a platform's tree) — has
no execution platform, and the transition is a **no-op**: the dependency is
analyzed in the parent's configuration
(`ExecutionTransitionFactory.ExecTransitionFinalizer.patch`,
`analysis/config/ExecutionTransitionFactory.java:192-197`). Otherwise the
execution platform is the one toolchain resolution selected — the host
platform, the only execution platform (docs/TOOLCHAINS.md) — and its label
is the PlatformInfo label, the end of an alias chain
(`@@platforms//host:host` for the default `--host_platform`). Extending the
lazy default host platform (docs/PLATFORMS.md, D2): a toolchain-using rule
whose toolchain resolution needed no platform resolves the host platform
when it has an exec edge, before any dependency; the default host platform
then needs the built-in profile (`--experimental-builtin-modules`) or an
explicit `--host_platform`, and fails explicitly as `While resolving
toolchains for target L (CONFIG): ...` otherwise.

**Exec options.** Bazel 9.3's exec transition is the built-in Starlark
`bazel_exec_transition` (`--experimental_exec_config` default,
`analysis/config/CoreOptions.java:97-108`;
`src/main/starlark/builtins_bzl/common/builtin_exec_platforms.bzl`) applied
over a baseline of **every native option at its default**
(`FunctionTransitionUtil.maybeGetExecDefaults`,
`analysis/starlark/FunctionTransitionUtil.java:167-225`), then the native
finalizer (`ExecutionTransitionFactory.java:192-268`). For the modelled
options:

| Option | Exec value | Source |
| --- | --- | --- |
| `compilation_mode` | the parent's `--host_compilation_mode` | `builtin_exec_platforms.bzl:221-229` |
| `host_compilation_mode` | carried | `:231-235` |
| `stamp` | `false` | `:226` |
| `strip` | `always` | `:291-348` (CppOptions) |
| `force_pic` | default (`false`) | not propagated |
| `define` | carried (`--experimental_exclude_defines_from_exec_config` is false) | `FunctionTransitionUtil.java:210-223` |
| `platforms` | `[execution platform]` | `ExecutionTransitionFactory.java:203-207` |
| `host_platform`, `extra_toolchains` | carried | `builtin_exec_platforms.bzl:411-419` (PlatformOptions) |
| `is exec configuration` | `true` | `:224` |
| `platform_suffix` | `exec` (`--experimental_exec_configuration_distinguisher=off`) | `CoreOptions.java:488-505`, `ExecutionTransitionFactory.java:255-258` |

`--extra_toolchains` **propagates** (PlatformOptions' `propagate` list), so
the exec configuration's registered toolchains include them. Starlark flags
are carried unless their scope is `target`
(`--incompatible_exclude_starlark_flags_from_exec_config` is false,
`FunctionTransitionUtil.getExecPropagatingStarlarkFlags`, `:231-251`). The
scope is the explicitly specified string `scope` attribute of the setting's
rule (skylib's settings, `label_flag`/`label_setting`); an omitted `scope` is
DEFAULT whatever the attribute's default
(`skyframe/BuildOptionsScopeFunction.java:180-190`). For each parsed flag,
an invalid value is Bazel's `Can't load flag --L: Invalid "scope" attribute
value "V". Allowed values: ["universal", "target", "project"].`
(`runtime/StarlarkOptionsParser.java:256-275`; among several invalid values
natively the first argument wins where Bazel iterates a HashMap); `project`
(project-boundary resets, PROJECT.scl) and a select()-valued `scope` fail
explicitly, but only after every flag's Bazel validation, so an invalid
scope is reported whatever the order (paired capture B1/project_and_bogus). Feature flags
(dropped by the finalizer, `:209-221`) do not exist natively. The transition
is idempotent: the exec configuration of an exec configuration with the same
execution platform is itself.

**Exec configurations** are interned in the build's `Configurations` and
analyzed like any other: select() sees the exec options (`config_setting`
`values`, `define_values`, flag values) and the execution platform's
constraints; toolchain resolution and the registered toolchains are
recomputed for the exec configuration (its target platform is the
execution platform); `ctx.build_setting_value` reads its flags; outputs live
under its root and its actions are `LABEL[CONFIG8]#N`.

**Exec output roots** follow Bazel exactly except for the CPU token.
`--experimental_platform_in_output_dir` defaults to `auto`, which an exec
configuration treats as yes (`CoreOptions.usePlatformInOutputDir`,
`analysis/config/CoreOptions.java:1146-1155`): its CPU/platform descriptor is
computed from its single target platform — the execution platform — with
the legacy heuristic (`--experimental_use_platforms_in_output_dir_legacy_heuristic`
default true, `CoreOptions.java:182-194`; no
`--experimental_override_platform_cpu_name`): the platform's **name**, unless
it is one of `host`, `host_platform`, `target_platform`, `default_host`,
`default_target` (`PlatformOptions.platformIsDefault`,
`analysis/PlatformOptions.java:43-50`), then the CPU (Bazel `k8`, natively
`rust`) (`OutputPathMnemonicComputer.handlePlatformCpuDescriptor` /
`computePlatformName`, `analysis/config/OutputPathMnemonicComputer.java:247-282`).
`platforms` is then marked explicit in the output path, so it never enters
the `ST-` hash; the baseline (`BuildConfigurationFunction.getBaselineOptions`,
`skyframe/config/BuildConfigurationFunction.java:133-174`, with
`BaselineOptionsFunction`, `skyframe/config/BaselineOptionsFunction.java:47-95`)
is the top-level options with the exec transition applied for the top-level
`--host_platform` label as given (`SkyframeExecutor.adjustForExec`,
`skyframe/SkyframeExecutor.java:1525-1572`) and the exec configuration's own
platform. Paired capture: `--host_platform=//p:linux` (also through the
alias `//p:linux_alias`) gives `linux-opt-exec` on both sides, `//p:mac`
`mac-opt-exec`, `--host_compilation_mode=dbg` `linux-dbg-exec`; the default
host platform (`@@platforms//host:host`, a default name) and
`--host_platform=@platforms//host` give Bazel's `k8-opt-exec` and the
native `rust-opt-exec` — no `ST-` hash. A platform name with `/` is Bazel's
InvalidMnemonicException `CPU/Platform descriptor 'D' is invalid as part of a
path: must not contain /` (`OutputPathMnemonicComputer.java:55-61`,
`vfs/PathFragment.java:948-957`), reported at the parent rule. Like Bazel,
two execution platforms with the same name share a root; natively every
exec configuration of one build has the same execution platform (the host
platform), so its outputs cannot collide, and action cache keys differ by
the configuration (`LABEL[CONFIG8]`).

**Remaining exec divergences (paired capture, tests/fixtures/exec_transition/reference_receipt.json):**
the CPU token `rust` where Bazel writes `k8` (D1); `ctx.bin_dir`,
`ctx.genfiles_dir`, `ctx.var` and `File.root` are absent (interpreter
`has no attribute` errors; N23c — adding them as erroring attributes would
change `dir(ctx)`); the CLI lists source files among a target's outputs
where Bazel's `--show_result` omits them; action reuse after another
configuration's build: Bazel's output tree is path-keyed, so an action whose
`bazel-out` output another build overwrote is re-run, while native outputs
live under their action key (`<cache>/actions/KEY/outputs/...`) and are
verified byte- and mode-exact against the manifest on every reuse
(`src/action.rs` `cache_valid`), so nothing can overwrite them and a hit is
always correct.

**genrule `tools`** are analyzed in the exec configuration; their files are
action inputs and are added to the `$(location)`/`$(locations)` entries of
their labels (merged with `srcs` entries, CommandHelper,
`analysis/CommandHelper.java:128-180`), never to `$(SRCS)`/`$<`
(`rules/genrule/GenRuleBase.java:95-110, 170-175`). Runfiles and executable
tools are not modelled (FilesToRunProvider: the files to build are used).

**Registered toolchains** are guarded per configuration: computing a
configuration's registered toolchains may analyze a registered target whose
exec edge computes the exec configuration's (nested, not a toolchain
cycle); a registered target needing its own configuration's registry is the
toolchain cycle report.

**Tests:** `tests/exec_transition.rs` (CLI), `src/engine.rs` (one engine
analyzing a target in two configurations: separate roots, `L` vs
`L[config8]` action ids, toolchain contexts and registries; cycles through
exec edges; nested registries), `src/config_registry.rs` (transition,
baseline, idempotence), `src/configuration.rs`
(`--host_compilation_mode`), `src/starlark_options.rs` (scopes).
`tests/configured_target_keys.rs` keeps the pre-N18a action keys of builds
without exec edges.

### Remaining observable differences (genuine capture run 4)

- `$(locations)` sorts paths as strings, as Bazel does (`LocationExpander.java:333-342`).
  Because native target roots are named `rust-<mode>` where Bazel uses `k8-<mode>`, a
  label present in both the target and an exec configuration with a platform-named exec
  root (for example `linux-opt-exec`) lists the two paths in the opposite order from
  Bazel (receipt row `B1/exec_probes/gboth`). The set of paths is the same.
- Errors raised while evaluating a `.bzl` file (for example the
  `--incompatible_disable_starlark_host_transitions` rejection of `cfg = "host"`) carry
  the same final message but use the native interpreter's traceback layout rather than
  Bazel's `Traceback (most recent call last): File ...` frames.
- Details of every capture row are in `tests/fixtures/exec_transition/reference_receipt.json`.

## Analysis order per target

`src/engine.rs` `Engine::analyze` follows Bazel's per-target order
(ConfiguredTargetFunction / `analysis/producers/PrerequisiteProducer`), as
confirmed by the paired capture (`D10/gap_order`, `T10`):

1. Load-time target checks (namespace, visibility of the target itself).
   A rule `cfg` transition fails first: it decides the configuration that
   everything else is evaluated in.
2. **Configuration conditions** (`ConfigConditionsProducer.java:91-172`): every
   `$config_dependencies` label (select keys of every attribute in rule-class
   attribute order, deduplicated, without `//conditions:default`;
   `AttributeProvider.java:443-466`, `BuildType.java:627-638`) is analyzed in
   the same configuration (so a broken `config_setting` reports its own error
   first). A key without a ConfigMatchingProvider fails with Bazel's text
   (`ConfigConditionsProducer.java:156-165`): `LOC: //:fg is not a valid
   select() condition for //:key.` + inspection and help lines. A missing key
   in an existing package is an assumed input file, hence also "not a valid
   select() condition"; a missing package is `no such package 'P': BUILD file
   not found in any of the following directories. ...`
   (`skyframe/PackageLookupFunction.java:125-155`). The invalid-condition
   message names the prerequisite's target, the end of an alias chain
   (`ConfiguredTargetAndData.getTargetLabel`). When a key fails to load or
   analyze, its own error is followed by `LOC: errors encountered resolving
   select() keys for L` at the consumer's location
   (`ConfigConditionsProducer.java:121-129, 200-211`). A `constraint_value`
   key is matched against the target platform when the consuming rule uses
   toolchain resolution and is otherwise not a valid condition
   (`ConfigConditions.java:64-83`, docs/PLATFORMS.md); a
   `config_setting(constraint_values = ...)` resolves the target platform
   before its own conditions.
3. Rule-level execution platform gaps (`exec_groups`, automatic exec
   groups), then toolchain resolution (docs/TOOLCHAINS.md) — Bazel resolves
   toolchains after the conditions and before dependency resolution.
4. Native classes without native analysis (everything but `filegroup`,
   `genrule`, `config_setting`, `alias`, `label_flag`, `label_setting`,
   `constraint_setting`, `constraint_value`, `platform`) and
   factory checks (`config_setting` all-empty / label-like keys) fail
   explicitly.
5. **validateAttributes** (`ConfiguredAttributeMapper.java:121-125`, called at
   `analysis/DependencyResolutionHelpers.java:309-313`): every configurable
   attribute is resolved in rule-class attribute order — `name`, built-in
   attributes, then Starlark attributes in `attrs` dict order — and the first
   failure is reported at the rule's location.
6. Remaining rule-level gaps (test/executable classes, late-bound defaults,
   implicit outputs, package-default gaps), then **gaps of resolved values**:
   dependency edges with `cfg` transitions other than exec, aspects, file/rule restrictions,
   label-keyed dictionaries and unmodelled built-in/native attribute values
   fail explicitly, only when the resolved value exercises them.
7. Dependencies are visited from **resolved values only**; the configured rule
   carries no unresolved select (`analysis.rs` rejects one as an internal
   error).
8. The config conditions are validated like direct prerequisites after the
   dependencies (`RuleContext.java:2104-2152`): visibility (with the
   DEFAULT_PUBLIC policy below), testonly and deprecation. Under DEFAULT_PUBLIC
   the validated prerequisite is the end of an alias chain
   (`condition.fromConfiguredTargetNoCheck(getActual())`, `:2125-2152`;
   `rules/AliasConfiguredTarget.java:229-233`): a `select()` key that is an
   alias checks the `config_setting`'s visibility against the consumer (the
   alias's own visibility is skipped) and the message names the
   `config_setting` (`target '//a:cs' is not visible from ...`).

Visibility failures (dependencies and conditions) use Bazel's
CommonPrerequisiteValidator text (`analysis/CommonPrerequisiteValidator.java:380-405`)
at the consuming rule: `LOC: in KIND rule L: Visibility error:\ntarget 'D' is
not visible from\ntarget 'L'\nRecommendation: modify the visibility declaration
if you think the dependency is legitimate. For more info see
https://bazel.build/concepts/visibility` (plus `. To set the visibility of that
source file target, use the exports_files() function` for source files).
Known divergences:

* Implicit (private Starlark attribute) dependencies: Bazel checks their
  visibility from the package of the rule definition's `.bzl` (falling back to
  the target's package) and prints that `.bzl` file as the consumer
  (`target '//pkg:defs.bzl'`; `consumerOrOwnerLocation`,
  `analysis/CommonPrerequisiteValidator.java:386-387`, with `isImplicitDep`
  at `:180-190`). The native profile still checks and reports them from the
  consuming target.
* Implicit Starlark attributes with `doc`: Bazel's missing-edge message adds
  `\nDocumentation for implicit attribute A of rules of type K:\nDOC`
  (`TargetUtils.java:405-412`); the native schema does not retain `doc`.

Missing dependency edges follow `TargetUtils.formatMissingEdge`
(`packages/TargetUtils.java:394-430`) at the consuming rule's location
(`analysis/producers/MissingEdgeError.java:86-111`,
`DependencyProducer.java:279-290`): an explicit dependency (native attributes,
public Starlark attributes, `alias.actual`, `flag_values` keys) appends ` and
referenced by 'L'`; an implicit one (private Starlark attributes, the
late-bound `:alias` of `label_flag`/`label_setting`) is `every rule of type
KIND implicitly depends upon the target 'D', but this target could not be found
because of: MESSAGE`. A missing package is first reported on its own, as
Bazel's package lookup does. Prerequisite errors raised by the rule context
(visibility, testonly) carry the consuming rule's location.

**File prerequisites.** Starlark `attr.label`/`attr.label_list` without
`allow_files`/`allow_single_file` allow no files and check labels strictly
(`analysis/starlark/StarlarkAttrModule.java:431-445`, `packages/Attribute.java:2349`):
the end of each alias chain must be a rule, else `LOC: in A attribute of K rule
L: KIND 'F' is misplaced here (expected no files)` (`source file` /
`generated file`, with the alias description), or `rule 'F' does not exist`
(`target` when the name has a `.`) for a missing input file
(`RuleContext.java:1819-1880`), all attribute errors reported.

**Cycles** use `AbstractLabelCycleReporter.maybeReportCycle`
(`skyframe/AbstractLabelCycleReporter.java:81-170`): `LOC: in KIND rule L:
cycle in dependency graph:` at the cycle head's location, the path to the cycle
indented by four spaces, then `.-> `, `|   `, `` `-- `` (`[self-edge]` for one
element), each key printed `LABEL (CONFIG)`. The path starts at the
requested target's top-level key: a requested rule that is not alias-like
(`AliasProvider.mayBeAlias`, `analysis/AliasProvider.java:168-176`) is
first requested in the untrimmed top-level configuration and analyzed in its
test-trimmed one (`TestTrimmingTransitionFactory.create`,
`analysis/test/TestTrimmingTransitionFactory.java:92-135`), so it is listed
twice — its untrimmed key, then its own — also when it is itself in the
cycle (then only the untrimmed key is on the path). The native
configurations are the trimmed ones (TestOptions are not modelled); the
untrimmed key's identity is the configuration's SHA-256 with a TestOptions
marker (`Configuration::untrimmed_id`). Divergence: CONFIG is the full
native `ConfigId`, not Bazel's BuildOptions checksum.

**Warnings** that are identical (same location and text) are reported once
per build, as Skyframe's EmittedEventState does
(`skyframe/EmittedEventState.java:32-52`): a dependency on a deprecated
target reached in two configurations (or through two attributes) warns once.

## Resolution semantics (`src/configured_attributes.rs`)

* Unconditional selects are simplified at loading for native and Starlark
  attributes alike (`BuildType.selectableConvert`, `packages/BuildType.java:165-211`):
  `select({"//conditions:default": v})` is `v`, and a `None` there is the
  type's default (`""`, `[]`, `{}`, `0`, `False` — not the Starlark
  `default=`), which also satisfies `mandatory=True`; a null label default
  leaves the attribute unset (`AttributeProvider.java:269-272`).
* `resolveSelector` (`ConfiguredAttributeMapper.java:277-381`): conditions in
  branch order; `InError` conditions are collected into `Unresolvable
  config_settings for configurable attribute "A" in L:` + one line each;
  matches keep only those not refined by another (`refines`,
  `ConfigMatchingProvider.java:204-227`: proper superset of settings, flag
  values or constraint values); several remaining matches are allowed only if
  their values are equal by Java `equals` (lists in order, dicts as entry sets
  regardless of order; a `None` branch counts as the type's default),
  otherwise `Illegal ambiguous match on configurable attribute ...`;
  otherwise `//conditions:default`; otherwise the no-match error
  (`:387-420`) with or without the custom `no_match_error`.
* `getResolvedAttribute` (`:157-193`): a chosen `None` is the attribute
  default (Starlark default, or the native type default), or `Mandatory
  attribute 'A' resolved to 'None' after evaluating 'select' expression` for a
  mandatory attribute; several elements are concatenated with `Type.concat`
  (`packages/Type.java`): lists append (`:774-780`), strings join (`:478-480`),
  ints add with signed 32-bit truncation (`:378-387`), dicts union keeping a
  key's first position and last value (`:604-610`, Guava `buildKeepingLast`;
  Guava is not vendored in the pinned tree — the order is confirmed by the
  paired capture rows `D4/concat/dict_*` and `T7/cat_*`).
  Booleans, labels, tristates and outputs reject `select() + ...` at loading
  (`BuildType.java:177-180`), for Starlark attributes too.
* `isAttributeValueExplicitlySpecified` (`:435-453`): an attribute whose every
  select chose `None` is unspecified, so `genrule(cmd = select({..: None}))`
  reports Bazel's missing-`cmd` error.

**Divergence:** the no-match error prints "configuration identifier" as the
first 7 hex digits of the native `ConfigId`, not Bazel's BuildOptions checksum;
`bazel config <id>` does not exist natively.

## `config_setting` (`src/config_setting.rs`)

`ConfigSetting.create` (`rules/config/ConfigSetting.java:111-166`) with the
existing load-time checks (label-like `values` keys, all-empty). Settings are
the `values` entries plus `define_values` as `define=K=V`, grouped by key in
first-seen order (`:169-258`). For each entry, `checkOptionValue` (`:420-482`):

* NON_CONFIGURABLE options: `error while parsing configuration settings:
  select() on 'X' is not allowed.` (`--incompatible_disable_select_on` is not
  modelled and defaults to empty);
* names that are not a Bazel 9.3 fragment option (after `oldName` mapping;
  INTERNAL options excluded, `BuildOptionDetails.java:56-84`): `unknown
  option: 'X'`;
* converter failures: `While parsing option --X=V: MESSAGE`;
* real Bazel options that are not modelled (for example `cpu`, test options):
  explicit `select() on build option 'X' is not implemented in the native
  profile` — never a guessed match;
* `optionMatches` (`:507-579`): single values by equality; `--define` as a
  multi-value map (last entry with the key decides; `<key K not found>`,
  `<empty>` diffs).

All entry errors are reported, each as `LOC: in values attribute of
config_setting rule L: ...` at the `config_setting`'s location.
`constraint_values` are matched against the target platform
(`diffConstraintValues`, docs/PLATFORMS.md). The option name table `src/bazel_options.rs` lists every
non-INTERNAL `@Option` of every `FragmentOptions` subclass in the pinned
source (including fragments Bazel may not register; those then fail as
"not implemented" rather than "unknown option").

**`flag_values`** (`UserDefinedFlagMatch`, `ConfigSetting.java:633-797`). Every
key is a prerequisite of the `config_setting`, analyzed in its configuration
before any check; then each edge is validated like `RuleContext.Builder`
(`analysis/RuleContext.java:1845-1880, 2165-2172`; `flag_values` allows no
files, `ConfigRuleClasses.java:292-294`): a key without a target (an assumed
input file that does not exist) is `rule 'L' does not exist` (`target 'L'
does not exist` if the name has a `.`), an existing file is `source file 'L'
is misplaced here (expected no files)` (`generated file` for outputs), then
visibility (a normal explicit dependency), testonly and deprecation. All
prerequisite errors are reported and stop the rule. Then, after the `values`
errors and in attribute order:

* the key resolves through aliases: specified label = the key, actual label
  = the end of the alias chain (for `label_flag`/`label_setting` keys this is
  the target the setting points to, `AliasConfiguredTarget.getLabel`,
  `rules/AliasConfiguredTarget.java:178-185`);
* without BuildSettingProvider: `error while parsing user-defined
  configuration values: flag_values keys must be build settings or feature
  flags and L is not` (no Bazel 9.3 rule of this profile provides
  `config_feature_flag`);
* label-typed settings canonicalize the expected value in the
  `config_setting`'s package (`maybeCanonicalizeLabel`, `:799-834`); the value
  converts with the setting's converter (`'V' cannot be converted to L type
  T`); the configured value is the command-line value or the default;
* list settings match if they contain the single expected value (`"V" not a
  valid value for flag L. Only single, exact values are allowed. ...`
  otherwise); other settings by equality. NoMatch diffs record `got` = the
  expected value and `want` = the configured one, as Bazel does;
* two keys with the same actual label: `flag 'A' referenced multiple times as
  ['K1', 'K2']` (`:771-787`; e.g. two label settings with the same default,
  paired capture row `A/build_go/private:default_nogo`).

All are `LOC: in flag_values attribute of config_setting rule L: ...`
attribute errors. The specified flag values (keyed by actual label) take part
in `refines` specialization.

## `alias`, `label_flag`, `label_setting` (`src/engine.rs`)

These are AliasConfiguredTargets (`rules/AliasConfiguredTarget.java:50-123`):

* `alias` (`rules/Alias.java:40-56`) depends on its `actual`, a `select()`
  resolved in the alias's configuration; `label_flag`/`label_setting`
  (`rules/LateBoundAlias.java:47-79`) on the command-line value or
  `build_setting_default` (`LabelBuildSettings.ACTUAL`,
  `rules/LabelBuildSettings.java:62-83`).
* Dependents see the end of the alias chain: its label (`ctx.attr.dep.label`),
  files, providers (BuildSettingProvider overridden by label settings,
  ConfigMatchingProvider, so an alias to a `config_setting` is a valid
  `select()` key) and kind (`allow_files`/testonly/deprecation checks use the
  actual target, `skyframe/ConfiguredTargetAndData.java:217-271`). Requesting
  an alias builds its actual's files.
* Visibility: the consumer checks the alias's own visibility and the alias
  checks its `actual`; label settings' `:alias` attribute is late-bound and not
  checked (`CommonPrerequisiteValidator.java:159-163`), so a default in another
  package may be private. Messages describe the chain
  (`AliasProvider.describeTargetWithAliases`, `analysis/AliasProvider.java:123-148`):
  `alias 'A' referring to target 'T'[ through 'B' -> 'C']`. Rules that can have
  any provider (these three) skip the testonly check of their own
  prerequisites (`:730-738`); testonly is checked between the consumer and
  the actual.
* Toolchain resolution: `alias` uses it only with select keys or
  `target_compatible_with` (`Alias.java:78-98`), so a `constraint_value` key
  of an alias is valid (docs/PLATFORMS.md); a non-empty
  `target_compatible_with` (and the other constraint/metadata attributes) fails
  explicitly as an analysis gap (incompatible target skipping is not
  implemented). Label settings never resolve toolchains
  (`LabelBuildSettings.java:99`).
* `Alias.create`'s `@bazel_tools//platforms` error compares
  `getCanonicalForm()` (`@@bazel_tools//...` in Bazel 9.3) with
  `@bazel_tools//platforms` and can never fire; it is not modelled.

**Visibility.** With Bazel's defaults
`--incompatible_enforce_config_setting_visibility=true` and
`--incompatible_config_setting_private_default_visibility=false`
(`pkgcache/PackageOptions.java:117-140`), the policy is DEFAULT_PUBLIC: a
`config_setting` without explicit `visibility` is public regardless of the
package default (`packages/Rule.java:694-710`); an explicit visibility is
enforced on the select edge.

## Consumers

* Starlark rules: `ctx.attr`/`ctx.files`/`ctx.file`/`ctx.outputs` and the
  `attr.*(allow_empty=False)` check see resolved values; built-in attributes
  (`features`, `exec_properties`, ...) too. `ctx.attr._config_dependencies` and
  `ctx.files._config_dependencies` are always `[]`: Bazel never resolves
  `$config_dependencies` as a prerequisite
  (`analysis/DependencyResolutionHelpers.java:408-416`).
* `filegroup` `srcs`, `genrule` `srcs`/`cmd`, `$(SRCS)`, `$(location)`:
  resolved values.
* Assumed input files: labels in select keys and branches of Starlark
  attributes (and the attribute default for `None` branches) are declared
  source files (`Package.java:893-920`,
  `AggregatingAttributeMapper.java:182-215`), like native ones.
* An assumed input file whose file does not exist is still a target (its
  `File` has the usual paths); it fails only where needed, as Bazel's
  ArtifactFunction does (`skyframe/ArtifactFunction.java:79-90, 404-430`): a
  requested target with a missing source fails with `LOC: //:t: missing input
  file '//:x'` lines and `LOC: N input file(s) do not exist`; an executed
  action consuming one with `LOC: PROGRESS failed: missing input file '//:x'`
  lines and `LOC: PROGRESS failed: N input file(s) do not exist`
  (`skyframe/ActionExecutionFunction.java:1543-1583`; PROGRESS is `Executing
  genrule //:g` for genrules, natively the action id for custom actions). Every
  source input is checked, including main-repository inputs below ignored
  top-level entries that the execroot does not plant (docs/IGNORED_DIRECTORIES.md). An undeclared name is Bazel's `no such target 'L': target 'N' not
  declared in package 'P' defined by BUILD` with the source-file/directory and
  did-you-mean suggestions (`packages/Package.java:335-396`,
  `packages/TargetSuggester.java`).
* Value-dependent gaps are evaluated on the resolved values, so an unchosen
  branch never fails and never visits its dependencies.
* `genrule` `outs`/`cmd`, `restricted_to` and `config_setting` errors carry
  the rule's location like Bazel's RuleContext errors.
