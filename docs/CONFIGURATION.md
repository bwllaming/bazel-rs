# Build configuration and configured attributes (Bazel 9.3)

Increment N16a: a native build configuration with the modelled Bazel options,
`config_setting` analysis for `values`/`define_values`, and `select()`
resolution during analysis. Everything else that a configuration would
influence keeps failing explicitly; nothing is ignored.

Pinned source: `/tmp/opencode/bazel-9.3-reference` (e89755b, Release 9.3.0).
Paths are relative to `src/main/java/com/google/devtools/build/lib/`. Code:
`src/configuration.rs`, `src/configured_attributes.rs`, `src/config_setting.rs`,
`src/engine.rs` (analysis order), `src/bazel_options.rs` (generated by
`scripts/extract_bazel_options.py`).

## Configuration

One configuration per `build` invocation (no transitions). Modelled options,
with Bazel's defaults and converters:

| Option | Default | Converter / normalization | Source |
| --- | --- | --- | --- |
| `-c`/`--compilation_mode` | `fastbuild` | `fastbuild`, `dbg`, `opt` (case-insensitive EnumConverter) | `analysis/config/CoreOptions.java:396-404`, `CompilationMode.java:24-51` |
| `--[no]stamp` | `false` | BooleanConverter (`true/1/yes/t/y`, `false/0/no/f/n`, any case) | `CoreOptions.java:349-355`, `common/options/Converters.java:46-60` |
| `--define NAME=VALUE` | `[]` | AssignmentConverter, repeatable; last value per key, sorted by key | `CoreOptions.java:255-267, 1245-1248`, `FragmentOptions.java:100-113` |
| `--strip` | `sometimes` | `always`, `sometimes`, `never` | `rules/cpp/CppOptions.java:337-347`, `CppConfiguration.java:119-134` |
| `--[no]force_pic` | `false` | BooleanConverter | `CppOptions.java:218-227` |
| `--platforms` (`--experimental_platforms`) | host platform | comma list, empty entries dropped, `//` prefixed unless `/`/`@`; only the first entry is kept; empty becomes `--host_platform` | `analysis/PlatformOptions.java:82-96, 189-200`, `skyframe/config/PlatformMappingValue.java:154-158`, `CoreOptionConverters.java:143-158, 331-361` |
| `--host_platform` (`--experimental_host_platform`) | `@bazel_tools//tools:host_platform` | label; empty means the default | `PlatformOptions.java:46-64, 218-227` |

Only the default host platform is modelled: `--platforms`/`--host_platform`
values that resolve to `@@bazel_tools//tools:host_platform` (or are empty) give
the default configuration, exactly like the unset options (both become
`platforms = [host]` after platform mapping); any other value fails with
`FORM requires platform analysis (N16c), which is not implemented in the native
profile; only the default host platform @@bazel_tools//tools:host_platform is
modelled`. `@bazel_tools` is always visible from the main repository (an
implicit dependency of every module), also when the native module graph does
not materialize it.

Command-line forms follow `OptionsParserImpl.identifyOptionAndPossibleArgument`
(`common/options/OptionsParserImpl.java:756-850`): `--name=value`,
`--name value`, `-c value`, `--name`/`--noname` for booleans (`--stamp true`
makes `true` a target pattern). Errors are Bazel's: exceptions that carry the
invalid argument are printed `ARG :: MESSAGE` (`runtime/BlazeOptionHandler.java:104,
628-637`) — `--nostamp=0 :: Unexpected value after boolean option: --nostamp=0`,
`--nocompilation_mode :: Illegal use of 'no' prefix on non-boolean option: ...`,
`-c=opt :: Invalid options syntax: -c=opt` (any `-x...` other than `-x`/`-x-`,
and `--=v`) — while `Expected value after ARG` and converter failures
(`While parsing option FORM: MESSAGE`) have no prefix. Label options are
converted with the main repository mapping. Every other option keeps the
existing `unsupported option ...; options are never silently ignored` error.
`query` accepts and validates the modelled CoreOptions (`-c`, `--[no]stamp`,
`--define`; `runtime/commands/QueryCommand.java:59-67`, which does not add the
configuration fragments' options, `runtime/BlazeCommandUtils.java:74-98`) and
ignores them (query is configuration-independent); `--strip`, `--force_pic`,
`--platforms` and `--host_platform` stay unsupported for `query`. A
workspace-root `platform_mappings` file (read by Bazel by default) fails the
build explicitly: platform mappings are not modelled.

**Identity.** `ConfigId` is SHA-256 over a versioned canonical JSON
serialization of the modelled values (plus Starlark build settings that differ
from their defaults, filled by N16b). Equal values give equal identities
regardless of spelling (`-c OPT` = `--compilation_mode=opt`). Analysis is keyed
by `ConfiguredTargetKey { label, config }`.

**Output paths.** Generated files live under `bazel-out/rust-<compilation_mode>/bin`
(Bazel's `<cpu>-<mode>` mnemonic, e.g. `k8-fastbuild`, with the native
profile's fixed `rust` part — a documented divergence). The default
configuration keeps `bazel-out/rust-fastbuild/bin`, so existing artifact paths,
action keys and caches are unchanged; options without an output-path effect
(`--stamp`, `--define`, ...) reuse the same action keys unless a resolved
attribute changes an action. The root is currently a per-thread value scoped
by the engine for the build's single configuration; it must become a
per-configured-target value before transitions (N18).

## Analysis order per target

`src/engine.rs` `Engine::analyze` follows Bazel's per-target order
(ConfiguredTargetFunction / `analysis/producers/PrerequisiteProducer`), as
confirmed by the paired capture (`D10/gap_order`, `T10`):

1. Load-time target checks (namespace, visibility of the target itself).
   A rule `cfg` transition fails first: it decides the configuration that
   everything else is evaluated in.
2. **Configuration conditions** (`ConfigConditionsProducer.java:91-172`): every
   `$config_dependencies` label (select keys of every attribute in rule-class
   attribute order, deduplicated, without `//conditions:default`;
   `AttributeProvider.java:443-466`, `BuildType.java:627-638`) is analyzed in
   the same configuration (so a broken `config_setting` reports its own error
   first). A key without a ConfigMatchingProvider fails with Bazel's text
   (`ConfigConditionsProducer.java:156-165`): `LOC: //:fg is not a valid
   select() condition for //:key.` + inspection and help lines. A missing key
   in an existing package is an assumed input file, hence also "not a valid
   select() condition"; a missing package is `no such package 'P': BUILD file
   not found in any of the following directories. ...`
   (`skyframe/PackageLookupFunction.java:125-155`).
3. Rule-level toolchain / execution platform resolution gaps
   (`toolchains`, `exec_groups`, `exec_compatible_with`) — Bazel resolves
   toolchains after the conditions and before dependency resolution.
4. Native classes without native analysis and factory checks
   (`config_setting` all-empty / label-like keys) fail explicitly.
5. **validateAttributes** (`ConfiguredAttributeMapper.java:121-125`, called at
   `analysis/DependencyResolutionHelpers.java:309-313`): every configurable
   attribute is resolved in rule-class attribute order — `name`, built-in
   attributes, then Starlark attributes in `attrs` dict order — and the first
   failure is reported at the rule's location.
6. Remaining rule-level gaps (test/executable classes, late-bound defaults,
   implicit outputs, package-default gaps), then **gaps of resolved values**:
   dependency edges with `cfg` transitions, aspects, file/rule restrictions,
   label-keyed dictionaries and unmodelled built-in/native attribute values
   fail explicitly, only when the resolved value exercises them.
7. Dependencies are visited from **resolved values only**; the configured rule
   carries no unresolved select (`analysis.rs` rejects one as an internal
   error).
8. The config conditions are validated like direct prerequisites after the
   dependencies (`RuleContext.java:2104-2152`): visibility (with the
   DEFAULT_PUBLIC policy below), testonly and deprecation.

Visibility failures (dependencies and conditions) use Bazel's
CommonPrerequisiteValidator text (`analysis/CommonPrerequisiteValidator.java:380-405`)
at the consuming rule: `LOC: in KIND rule L: Visibility error:\ntarget 'D' is
not visible from\ntarget 'L'\nRecommendation: modify the visibility declaration
if you think the dependency is legitimate. For more info see
https://bazel.build/concepts/visibility` (plus `. To set the visibility of that
source file target, use the exports_files() function` for source files).
Known divergences:

* Implicit (private Starlark attribute) dependencies: Bazel checks their
  visibility from the package of the rule definition's `.bzl` (falling back to
  the target's package) and prints that `.bzl` file as the consumer
  (`target '//pkg:defs.bzl'`; `consumerOrOwnerLocation`,
  `analysis/CommonPrerequisiteValidator.java:386-387`, with `isImplicitDep`
  at `:180-190`). The native profile still checks and reports them from the
  consuming target.
* Missing dependency edges: for an explicit dependency Bazel appends
  ` and referenced by '//x:y'` to the `no such target`/`no such package`
  message (`TargetUtils.formatMissingEdge`, `packages/TargetUtils.java:398-403`;
  implicit attributes get their attribute documentation instead); the native
  profile prints the message without that suffix.

## Resolution semantics (`src/configured_attributes.rs`)

* Unconditional selects are simplified at loading for native and Starlark
  attributes alike (`BuildType.selectableConvert`, `packages/BuildType.java:165-211`):
  `select({"//conditions:default": v})` is `v`, and a `None` there is the
  type's default (`""`, `[]`, `{}`, `0`, `False` — not the Starlark
  `default=`), which also satisfies `mandatory=True`; a null label default
  leaves the attribute unset (`AttributeProvider.java:269-272`).
* `resolveSelector` (`ConfiguredAttributeMapper.java:277-381`): conditions in
  branch order; `InError` conditions are collected into `Unresolvable
  config_settings for configurable attribute "A" in L:` + one line each;
  matches keep only those not refined by another (`refines`,
  `ConfigMatchingProvider.java:204-227`: proper superset of settings, flag
  values or constraint values); several remaining matches are allowed only if
  their values are equal by Java `equals` (lists in order, dicts as entry sets
  regardless of order; a `None` branch counts as the type's default),
  otherwise `Illegal ambiguous match on configurable attribute ...`;
  otherwise `//conditions:default`; otherwise the no-match error
  (`:387-420`) with or without the custom `no_match_error`.
* `getResolvedAttribute` (`:157-193`): a chosen `None` is the attribute
  default (Starlark default, or the native type default), or `Mandatory
  attribute 'A' resolved to 'None' after evaluating 'select' expression` for a
  mandatory attribute; several elements are concatenated with `Type.concat`
  (`packages/Type.java`): lists append (`:774-780`), strings join (`:478-480`),
  ints add with signed 32-bit truncation (`:378-387`), dicts union keeping a
  key's first position and last value (`:604-610`, Guava `buildKeepingLast`;
  Guava is not vendored in the pinned tree — the order is confirmed by the
  paired capture rows `D4/concat/dict_*` and `T7/cat_*`).
  Booleans, labels, tristates and outputs reject `select() + ...` at loading
  (`BuildType.java:177-180`), for Starlark attributes too.
* `isAttributeValueExplicitlySpecified` (`:435-453`): an attribute whose every
  select chose `None` is unspecified, so `genrule(cmd = select({..: None}))`
  reports Bazel's missing-`cmd` error.

**Divergence:** the no-match error prints "configuration identifier" as the
first 7 hex digits of the native `ConfigId`, not Bazel's BuildOptions checksum;
`bazel config <id>` does not exist natively.

## `config_setting` (`src/config_setting.rs`)

`ConfigSetting.create` (`rules/config/ConfigSetting.java:111-166`) with the
existing load-time checks (label-like `values` keys, all-empty). Settings are
the `values` entries plus `define_values` as `define=K=V`, grouped by key in
first-seen order (`:169-258`). For each entry, `checkOptionValue` (`:420-482`):

* NON_CONFIGURABLE options: `error while parsing configuration settings:
  select() on 'X' is not allowed.` (`--incompatible_disable_select_on` is not
  modelled and defaults to empty);
* names that are not a Bazel 9.3 fragment option (after `oldName` mapping;
  INTERNAL options excluded, `BuildOptionDetails.java:56-84`): `unknown
  option: 'X'`;
* converter failures: `While parsing option --X=V: MESSAGE`;
* real Bazel options that are not modelled (for example `cpu`, test options):
  explicit `select() on build option 'X' is not implemented in the native
  profile` — never a guessed match;
* `optionMatches` (`:507-579`): single values by equality; `--define` as a
  multi-value map (last entry with the key decides; `<key K not found>`,
  `<empty>` diffs).

All entry errors are reported, each as `LOC: in values attribute of
config_setting rule L: ...` at the `config_setting`'s location. Non-empty `flag_values` (N16b) and `constraint_values` (N16c)
fail explicitly. The option name table `src/bazel_options.rs` lists every
non-INTERNAL `@Option` of every `FragmentOptions` subclass in the pinned
source (including fragments Bazel may not register; those then fail as
"not implemented" rather than "unknown option").

**Visibility.** With Bazel's defaults
`--incompatible_enforce_config_setting_visibility=true` and
`--incompatible_config_setting_private_default_visibility=false`
(`pkgcache/PackageOptions.java:117-140`), the policy is DEFAULT_PUBLIC: a
`config_setting` without explicit `visibility` is public regardless of the
package default (`packages/Rule.java:694-710`); an explicit visibility is
enforced on the select edge.

## Consumers

* Starlark rules: `ctx.attr`/`ctx.files`/`ctx.file`/`ctx.outputs` and the
  `attr.*(allow_empty=False)` check see resolved values; built-in attributes
  (`features`, `exec_properties`, ...) too. `ctx.attr._config_dependencies` and
  `ctx.files._config_dependencies` are always `[]`: Bazel never resolves
  `$config_dependencies` as a prerequisite
  (`analysis/DependencyResolutionHelpers.java:408-416`).
* `filegroup` `srcs`, `genrule` `srcs`/`cmd`, `$(SRCS)`, `$(location)`:
  resolved values.
* Assumed input files: labels in select keys and branches of Starlark
  attributes (and the attribute default for `None` branches) are declared
  source files (`Package.java:893-920`,
  `AggregatingAttributeMapper.java:182-215`), like native ones.
* An assumed input file whose file does not exist is still a target (its
  `File` has the usual paths); it fails only where needed, as Bazel's
  ArtifactFunction does (`skyframe/ArtifactFunction.java:79-90, 404-430`): a
  requested target with a missing source fails with `LOC: //:t: missing input
  file '//:x'` lines and `LOC: N input file(s) do not exist`; an executed
  action consuming one with `LOC: PROGRESS failed: missing input file '//:x'`
  lines and `LOC: PROGRESS failed: N input file(s) do not exist`
  (`skyframe/ActionExecutionFunction.java:1543-1583`; PROGRESS is `Executing
  genrule //:g` for genrules, natively the action id for custom actions). Every
  source input is checked, including main-repository inputs below ignored
  top-level entries that the execroot does not plant (docs/IGNORED_DIRECTORIES.md). An undeclared name is Bazel's `no such target 'L': target 'N' not
  declared in package 'P' defined by BUILD` with the source-file/directory and
  did-you-mean suggestions (`packages/Package.java:335-396`,
  `packages/TargetSuggester.java`).
* Value-dependent gaps are evaluated on the resolved values, so an unchosen
  branch never fails and never visits its dependencies.
* `genrule` `outs`/`cmd`, `restricted_to` and `config_setting` errors carry
  the rule's location like Bazel's RuleContext errors.

## Paired capture

`artifacts/n16a-capture.py` runs every step of `tests/configuration.rs` and
the design scenarios against genuine Bazel 9.3.0 and the native binary; the
tracked summary is `tests/fixtures/configuration/reference_receipt.json`
(verdicts per row, exact Bazel strings of every mismatch, run history).
Run 1 (first candidate): 22 EXACT, 77 EXACT_MESSAGE, 24 EXPECTED_NATIVE_UNSUPPORTED,
186 MISMATCH. Run 2 (after the review fixes; 329 rows): 164 EXACT, 99
EXACT_MESSAGE, 23 EXPECTED_NATIVE_UNSUPPORTED, 43 MISMATCH, of which 13 differ
only in the `rust-`/`k8-` output path mnemonic, 2 (`T11/consume_missing_opt`,
`T11/files_missing_opt`) were fixed after the capture (recorded in the
receipt), and the rest are listed below or are explicit N16b/N16c failures
(toolchain resolution, non-default platforms, `flag_values`). Remaining
documented divergences:

* Generated paths `bazel-out/rust-<mode>/bin` versus `k8-<mode>`.
* The configuration identifier in no-match errors is the native SHA-256, not
  Bazel's BuildOptions checksum.
* `dict | select(...)` (dict on the left) and Starlark binary-operator error
  wording (`Operation ... not supported` versus `unsupported binary
  operation: X op Y`) come from the vendored interpreter.
* `ctx.var` and `ctx.bin_dir` are absent from the native `ctx` (pre-existing).
* The CLI lists source files of a source-only filegroup; Bazel prints
  `(nothing to build)`.
* Starlark-level locations (load-time conversion errors, `fail()` in a rule
  implementation) point at the native interpreter's span.
* `flag_values` (N16b), `constraint_values`/platforms and toolchain
  resolution (N16c) fail explicitly where Bazel evaluates them.
* `query --strip=...` (and the other non-CoreOptions modelled options) is an
  explicit unsupported option; Bazel says `--strip=always :: Unrecognized
  option: --strip=always` with SpellChecker suggestions over every query option.
* A custom action consuming a missing input reports its action id where Bazel
  prints the action's progress message (genrules match exactly).

## Explicitly unsupported (unchanged boundaries)

* `--//label=value` Starlark build setting overrides and `flag_values`
  matching (N16b); `constraint_values`, platforms, `constraint_value` select
  keys, toolchain resolution (N16c).
* `alias`, `label_flag`, `label_setting`, `constraint_setting`,
  `constraint_value`, `platform`, `toolchain` analysis (also as select keys).
* Configuration transitions (rule and attribute `cfg`), `--flag_alias`,
  `--debug_select_always_succeed`, `--incompatible_disable_select_on`,
  platform mappings, non-default `--platforms`/`--host_platform`, every other
  build option, `cquery`/`config` commands.
