# C++ toolchains: `cc_toolchain_config`, `cc_toolchain`, `cc_toolchain_alias`

Bazel 9.3 (`e89755babf3e941bc1e9d8120b1cd48854ab9dfa`) no longer implements
the C++ toolchain rules in Java: rules_cc 0.2.17's compatibility proxy
(`@cc_compatibility_proxy//:symbols.bzl`) routes `cc_common`, `CcInfo` and
`CcToolchainConfigInfo` to rules_cc's own Starlark, and `cc_toolchain`
(`cc/private/rules_impl/cc_toolchain.bzl`) and `cc_toolchain_alias`
(`cc_toolchain_alias.bzl`) are Starlark rules. The native profile analyzes the
**genuine** rule sets end to end; what it adds are the Bazel built-ins they
reach. Citations: `J = src/main/java/com/google/devtools/build/lib` of the
pinned tree.

## What is analyzed

- **`cc_toolchain_config` rules** (N25d4): any rule returning rules_cc's
  `CcToolchainConfigInfo` — a main-repository config with fixed tool paths,
  rules_cc's `unix_cc_toolchain_config` as generated by the genuine
  `cc_configure` extension for `@local_config_cc//:local` (it reads
  `ctx.fragments.apple`/`cpp` and its `_xcode_config` =
  `configuration_field("apple", "xcode_config_label")` →
  `@bazel_tools//tools/cpp:host_xcodes` → `@local_config_xcode//:host_xcodes`,
  apple_support's `xcode_config` with no versions, whose `XcodeVersionInfo` is
  native, docs/XCODE_VERSION_INFO.md), the armeabi stub config, and
  hermetic_cc_toolchain 4.1.0's `zig_cc_toolchain_config`.
- **`cc_toolchain`** (N25d5) in the target and exec configurations: every
  attribute of the genuine rule, including the late-bound
  `_libc_top`/`_zipper` (`configuration_field("cpp", ...)`, `None` by
  default, docs/SUBRULES.md), `libc_top` (sysroot from its package), the exec
  `_interface_library_builder`/`_link_dynamic_library_tool` files, the exec
  `_aggregate_ddi`/`_generate_modmap` filegroups (a `select()` on
  `@platforms//os:windows`), the `_whitelist_disabling_parse_headers_and_layering_check_allowed`
  package group (`PackageSpecificationInfo`), the build-info translator
  `@bazel_tools//tools/build_defs/build_info:cc_build_info` (an
  `OutputGroupInfo`, below), and the `create_fdo_context` subrule. It returns
  rules_cc's `CcToolchainInfo` (a Starlark provider), `ToolchainInfo(cc = ...,
  cc_provider_in_toolchain = True)`, `TemplateVariableInfo` (the toolchain's
  `make_variables` without `CC_FLAGS`, `STACK_FRAME_UNLIMITED`, the global
  `CC`/`AR`/`NM`/`LD`/`STRIP`/`OBJCOPY`/`C_COMPILER`/`CROSSTOOLTOP`/`ABI`/
  `ABI_GLIBC_VERSION`/`GLIBC_VERSION` variables and the `CC_FLAGS` of the
  `cc-flags-make-variable` action) and `DefaultInfo(files = all files + libc)`.
- **`cc_toolchain_alias`** (`@rules_cc//cc:current_cc_toolchain`, and
  `@bazel_tools//tools/cpp:current_cc_toolchain` aliasing it): resolves the
  optional `@bazel_tools//tools/cpp:toolchain_type` and forwards the same
  providers (its TemplateVariableInfo has no `CC_FLAGS`).
- Consumers: `find_cc_toolchain`, `cc_common.configure_features` (rules_cc's
  `configure_features`, which requests the compilation mode, `nonhost`/`host`
  only with `--noincompatible_dont_enable_host_nonhost_crosstool_features`,
  docs below), `create_compile_variables`, `create_link_variables`, and the
  feature engine of docs/CC_FEATURES.md (command lines, environments, tools,
  execution requirements).

In the exec configuration the toolchain sees `-c opt` and
`ctx.configuration.is_tool_configuration() == True` (`_is_tool_configuration`),
so the compilation-mode features flip to `opt`.

Provider payloads that cross frozen dependency boundaries (`CcToolchainInfo`
fields) now include `PackageSpecificationInfo` (owned `Arc` DAG, file-free),
C++ build `Variables` (traversed: File-valued variables are inputs),
`CcToolchainFeatures`/`FeatureConfiguration` (owned data; the configuration
cache is a `Mutex`, so concurrent analyses of consumers share one frozen
instance safely, `src/cc_features/tests.rs`), the artifact-free
`HeaderInfo`, the `cpp` fragment, and Starlark `def`/lambda functions
(`CcToolchainInfo.static_runtime_lib` etc.). Functions are opaque to the
provider-file walk: a File reachable only through a closure is not a known
input of a consumer and fails explicitly if used as one (`action input ... is
not a dependency or declared output`; rules_cc also stores the captured
depsets as plain fields).

## Build info (`bazel_cc_build_info`)

The genuine translator declares, for `non_redacted_build_info_files`,
`actions.transform_version_file`/`transform_info_file` outputs
(`volatile_file.h`, `non_volatile_file.h`) and, for
`redacted_build_info_files`, `actions.symlink` of the redacted template
(docs/ACTIONS_PARAMS.md). Analysis and the redacted symlink execute natively;
**executing the stamped outputs is an explicit failure** (`workspace status
(build info) transformation is not supported by the native profile`), as is
demanding them through any consumer.

## Explicit gaps

- The common `toolchains` attribute (`toolchains = ["@rules_cc//cc:current_cc_toolchain"]`
  for `$(CC)`/`$(CC_FLAGS)` in a genrule or `ctx.var`) is still rejected
  (`attribute 'toolchains' ... (TemplateVariableInfo Make variables)`);
  `ctx.var` of a rule that resolves the C++ toolchain type does include the
  toolchain's variables (docs/CTX_SURFACE.md).
- `--noincompatible_dont_enable_host_nonhost_crosstool_features` is an
  unsupported option, so `host`/`nonhost` are never requested (Bazel's
  default, `J/rules/cpp/CppOptions.java:752-760`).
- `dynamic_runtime_lib` (`cc_common.solib_symlink_action`), `module_map`
  (`cc_common.create_module_map` with an artifact), header artifacts in
  `create_header_info`, FDO/propeller/memprof profiles, `cc_common.compile`
  and `link` (cc_library/cc_binary), C++ modules, coverage, and Windows/macOS
  toolchains fail explicitly where reached.
- `Label.relative`/`workspace_root`/`workspace_name` stay available under
  `--noincompatible_enable_deprecated_label_apis` (Bazel hides them).
- The `_hidden_top_level_INTERNAL_` group of an executable (or test) target:
  Bazel puts its runfiles tree artifact there (`RuleConfiguredTargetBuilder.java:155-158`,
  `RunfilesSupport.getRunfilesTreeArtifact`); the native profile has no
  runfiles-tree artifact and lists the default runfiles' artifacts, as for
  every other rule (`:159-173`).
- A File reachable only through a Starlark closure inside a provider (opaque
  to the provider-file walk) used as an action input fails with
  `action input <path> is not a dependency or declared output`
  (tests/output_group_info.rs).
- Output paths use the native `rust-<mode>` mnemonics (docs/CONFIGURATION.md
  D1), so `ctx.bin_dir`-derived values such as
  `CcToolchainInfo.dynamic_runtime_solib_dir` read
  `bazel-out/rust-fastbuild/bin/_solib__...` where Bazel prints
  `bazel-out/k8-fastbuild/bin/_solib__...`.
