# Building bazel-rs with Bazel (self-build)

Cargo stays the primary build: tests, releases and rust-analyzer use Cargo
(`cargo test --locked`, scripts/release.py). Beside it, the repository is a
Bazel 9.3.1 workspace that builds the same crate with rules_rust. That is a
dogfood check: bazel-rs builds itself, and genuine Bazel must agree with it on
every action key.

## Files

| File | What it does |
|---|---|
| `MODULE.bazel` | rules_rust 0.75.0 (the first release whose checksums include Rust 1.99.0; ~/code's 0.74.0 stops at 1.98), rules_cc, platforms, bazel_skylib. The Rust toolchain is `rust-toolchain.toml`'s channel (tests/test_self_build.py checks that they match). `crate.from_cargo` resolves the third-party crates from `Cargo.toml` and `Cargo.lock`, so there is no second lockfile. |
| `MODULE.bazel.lock` | Not committed (`.gitignore`): each checkout writes its own (see [The lockfile](#the-lockfile)). Genuine 9.3.1 and bazel-rs write the same bytes. |
| `BUILD.bazel` | `//:bazel_rs` (the library), `//:bazel-rs` (the binary, with the `jemalloc` default feature), `//:unit_tests` (`cargo test --lib`) and 12 integration tests. |
| `self_build.bzl` | Turns an integration test into a `rust_test` that runs the Bazel-built binary (see [Integration tests](#integration-tests)). |
| `.bazelignore` | `target/`, `.direnv/`, `artifacts/`, `.git/`, `bazel-rs-out/`, and each test fixture directory with a BUILD file (these are separate workspaces, not packages). Generated by `scripts/self_build.py bazelignore`. tests/test_self_build.py fails when the list is out of date. |
| `.bazelrc`, `.bazelversion` | `test --test_output=errors`. 9.3.1, the compatibility target. |
| `scripts/self_build.py` | The `check`, `compare` and `bazelignore` commands. |

Cargo.toml stays the source of truth:

- Third-party crates come through `all_crate_deps()`.
- Lints come from its `[lints]` table through `extract_cargo_lints`, which adds `--deny=unsafe_code`.
- `CARGO_PKG_VERSION` comes from its `version` line through the `:cargo_pkg_version` genrule and `rustc_env_files`.

`build.rs` compiles C only for musl targets, so the gnu build has no build
script of its own. The C code of ring, blake3 and tikv-jemalloc-sys is built
by their own build scripts (`cargo_build_script`), using the auto-configured
host C toolchain. jemalloc's script also needs `make` and `sh`.

crate_universe writes `vendor/*/BUILD.bazel` for the `[patch.crates-io]` path
crates. Genuine Bazel does the same. These files are listed in `.gitignore`.

## The lockfile

`MODULE.bazel.lock` is per checkout. crate_universe (rules_rust 0.75.0)
resolves the `[patch.crates-io]` path crates of Cargo.toml to
`local_crate_mirror` repositories whose `path` is absolute (the checkout's
`vendor/starlark-0.14.2`, from `cargo metadata`). `crate.from_cargo` without a
crate_universe `lockfile` declares the extension non-reproducible, so Bazel
records that result, the absolute path included, in MODULE.bazel.lock and
reuses it as long as Cargo.toml, Cargo.lock and the extension's code are
unchanged — in any other checkout as well. Genuine 9.3.1 fails there exactly
like bazel-rs (`can't readdir(), not a directory: <the other checkout>/vendor/…`;
seen on CI with the first committed lockfile). Neither crate_universe option
avoids it: its own `lockfile` (a second lockfile to maintain) records the same
absolute path. tests/test_self_build.py fails if a tracked MODULE.bazel.lock
holds an absolute path.

## Running

```sh
python3 scripts/self_build.py check                      # bazel-rs on PATH, cache in ~/.cache/bazel-rs/self-build
python3 scripts/self_build.py check --bazel /path/to/bazel-9.3.1 --state-dir /tmp/x   # genuine (--batch)
python3 scripts/self_build.py compare --genuine /path/to/bazel-9.3.1 --bazel-rs bazel-rs --work-dir /tmp/empty
```

`check` does three things:

1. Builds `//:bazel-rs`.
2. Runs scripts/release.py's offline smoke test on the result: `--version`, `version`, `help`, then a query and two builds of a genrule workspace.
3. Runs `test //...`.

It passes `--nosystem_rc --nohome_rc`, so only the workspace `.bazelrc` applies.

`compare` starts its own loopback HTTP/1.1 remote cache. It then makes four
cold builds, each with fresh local state:

1. Genuine fills an empty cache.
2. bazel-rs reads that cache.
3. bazel-rs fills a second empty cache.
4. Genuine reads the second cache.

It prints the remote cache hits and the cache traffic of each build.

CI (`.github/workflows/ci.yml`, job `self-build`, self-hosted) downloads the
newest release of this repository with `gh release download` and the job's
`GITHUB_TOKEN`. It uses the static x86_64 archive and checks its `.sha256`. Then
it runs `check` with that binary. The cache stays in
`~/.cache/bazel-rs/self-build` on the runner. The comparison with genuine Bazel
is local only.

## Integration tests

Cargo compiles `env!("CARGO_BIN_EXE_bazel-rs")` to the binary's absolute path.
Under Bazel, only a runfiles path is known at compile time. `rustc_env` with
`$(rootpath)` is not enough: the tests run the binary with `current_dir` set
to a scratch workspace, and a relative program path resolves against that
directory.

So `bazel_rs_integration_test` copies the test with that one macro call
replaced by `crate::__self_build_bazel_rs()`, which returns
`$TEST_SRCDIR/_main/bazel-rs`. It places the copy under `self_build/tests/`,
next to a copy of `tests/support/*.rs`, so the relative `include!`s still
resolve. The Cargo sources are unchanged.

The tests that need no binary are compiled from `tests/` directly, with
`CARGO_MANIFEST_DIR` set to `"."` (the runfiles root). Every test gets
`.cargo/config.toml`'s `BAZEL_RS_RESULT_LINES=1`.

| Group | Tests |
|---|---|
| No binary | `cquery_proto_streaming`, `libc_string`, `observed_fs_discipline`, `spawn_discipline`, `staging_bench` |
| Bazel-built binary | `bazelrc`, `cquery`, `custom_rules`, `definition_bzl_cache`, `glob_symlinks`, `provider_init`, `string_list_dict` |

All 12 are in scripts/ci-integration-tests.txt, which tests/test_self_build.py
checks.

`//:unit_tests` skips two tests. Both need this crate's `Cargo.toml` or
`Cargo.lock` to be a settled file, with a ctime older than the racy margin.
bazel-rs stages a test's runfiles as fresh hard links of its store blobs, so
the ctime is new. Genuine Bazel stages symlinks into the source tree, and
there the two tests pass. They are skipped for both binaries, so the action
keys stay the same.

## Measurements (2026-11-03, 64 cores, shared host with load 9–26, `nice -n 10`)

Same commit; bazel-rs 0.4.8+main (d07bd5f5), genuine 9.3.1. Each binary has
its own cache.

| Build `//:bazel-rs` (fastbuild) | genuine 9.3.1 | bazel-rs |
|---|---:|---|
| Cold, including repository fetch | 243.6 s; 202.9 s | 222.7 s; 199.6 s |
| Cold, release 0.4.8 musl (CI binary, linux-sandbox) | — | 197.5 s |
| No-op rebuild (genuine: warm server) | 0.33–0.42 s | 0.33–0.35 s |
| Incremental: one comment line appended to src/ui.rs | 53.0 s | 54.9 s |
| The edit reverted | 51.0 s | 0.40 s (action cache hit on the earlier key) |
| `test //...` after the build, 13 tests | 85.2 s | 91.0 s (release 0.4.8) |

Both binaries run 759 spawns (rustc, build scripts, genrules) and write
byte-identical `MODULE.bazel.lock` files.

Remote cache cross-hits (`compare`; every build starts from empty local state):

| Round | Build | Role | Seconds | Processes | Remote cache hits | Cache traffic |
|---|---|---|---:|---:|---:|---|
| genuine → bazel-rs | genuine | fill | 202.9 | 1176 | 0 | 759 AC misses, 759 AC puts, 2287 CAS puts |
| genuine → bazel-rs | bazel-rs | read | 28.5 | 1025 | **759** | 759 AC hits, 61 CAS hits |
| bazel-rs → genuine | bazel-rs | fill | 199.6 | 1025 | 0 | 759 AC misses, 759 AC puts, 2287 CAS puts |
| bazel-rs → genuine | genuine | read | 34.5 | 1176 | **759** | 759 AC hits, 104 CAS hits |

All 759 action keys match in both directions, and both binaries upload the
same number of entries.

The Rust-only outputs are byte-identical between the two binaries. The C
objects of ring, blake3 and jemalloc are not: their debug info contains the
absolute sandbox path, which differs between any two output bases. A read
build downloads the outputs of the fill build, so this does not cost cache
hits.

## Differences seen (not bugs of this check)

- **Process summary counts.** Genuine counts 151 more "internal" processes
  (417 against 266). These are mostly the `.params` file writes, which bazel-rs
  does not materialize as separate actions.
- **"action cache hit" counts.** In an incremental build, bazel-rs reports
  1020 hits, because every process consults the action cache. A genuine
  server reports 1, because only dirty actions are checked. A genuine
  `--batch` no-op build reports 1175, the same kind of count as bazel-rs.
- **Fixed in this branch.** `TEST_BINARY` of a root-package test is
  `./unit_tests`, as in genuine `PathFragment.getCallablePathString`. bazel-rs
  used to give `unit_tests`.
